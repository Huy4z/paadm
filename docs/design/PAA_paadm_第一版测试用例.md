# PAA / paadm 第一版测试用例（TDD 初稿）

- 版本：v0.1
- 测试对象：`paadm` Rust CLI、业务逻辑与 SQLite 数据存储
- 测试目标：先建立可靠的数据管理核心，再由 Agent 调用
- 不在本轮测试：自然语言意图识别、LLM 提示词、QQ/微信消息收发、闲聊功能

---

## 1. 测试范围与约定

### 1.1 第一版目标

1. paadm 能正常启动、解析命令并输出约定格式。
2. paadm 能创建、查询、修改、删除业务数据。
3. 数据能写入 SQLite，并在进程退出、重新启动后保留。
4. 输入错误、目标不存在等情况能被明确处理。
5. Agent 可以依赖稳定的 JSON 输出判断操作结果。
6. 数据关联和事务操作不会产生明显的数据不一致。

### 1.2 第一版业务范围

| 领域 | 第一版操作 |
|---|---|
| Task（待办） | 创建、列表查询、按 ID 查询、修改、完成、删除 |
| Schedule（日程） | 创建、列表查询、按 ID 查询、修改、删除 |
| Reminder（提醒） | 创建、列表查询、修改、取消/删除 |
| Transaction（账目） | 创建收入/支出、查询、修改、删除 |
| Note（想法/临时记录） | 创建、查询、修改、删除 |
| Storage（存储） | 初始化、持久化、事务、错误处理 |
| CLI（命令行） | 参数解析、JSON 输出、退出码、帮助信息 |

建议按纵向切片推进：先完整实现 Task（CLI → Service → Repository → SQLite），再复用已验证的模式实现其他领域。不要一开始同时铺开所有模块。

### 1.3 通用测试约定

- 每个测试使用独立的临时 SQLite 数据库，禁止依赖开发者机器上的真实 `paa.db`。
- 测试数据使用固定 ID 或由测试环境生成的 ID，不依赖随机结果。
- 日期时间使用明确的 ISO 8601 格式并带时区，例如 `2026-11-17T15:00:00+08:00`。
- 测试不得依赖真实等待、系统通知或外部网络。
- 查询结果顺序必须有明确规则；若接口没有承诺顺序，测试不得假定顺序。
- 测试结束后清理临时数据库及相关文件。
- JSON 模式下 stdout 只包含 JSON；日志和诊断信息写入 stderr。

### 1.4 通用 JSON 响应约定

成功：

```json
{
  "success": true,
  "data": { "id": "task_001" },
  "error": null
}
```

失败：

```json
{
  "success": false,
  "data": null,
  "error": {
    "code": "TASK_NOT_FOUND",
    "message": "Task does not exist"
  }
}
```

建议约定：成功退出码为 `0`；业务错误和参数错误使用非零退出码。Agent 应依赖稳定的 `error.code` 判断错误类型，不应依赖易变的自然语言 `message`。

## 11. 推荐 TDD 实施顺序

不要按编号一次性写完所有测试。每次只围绕一个小闭环工作。

### 第一阶段：打通最小链路

1. CLI-001：帮助信息。
2. DB-001：数据库初始化。
3. TASK-001：创建最小待办。
4. TASK-010：按 ID 查询。
5. TASK-014：空列表。
6. DB-003：重启后数据仍然存在。
7. CLI-005：JSON 成功输出。
8. CLI-006：JSON 失败输出。

完成标准：能通过 CLI 创建待办，退出程序后重新启动，仍能查询到待办。

### 第二阶段：完善 Task

1. TASK-003 / TASK-004：输入校验。
2. TASK-012：状态筛选。
3. TASK-016 / TASK-017：修改。
4. TASK-020：完成待办。

7. TASK-011 / TASK-019：不存在记录的错误处理。

完成标准：Task 的基本 CRUD 和状态变更都有自动化测试。

### 第三阶段：完善数据可靠性

1. DB-006：SQL 参数安全。

完成标准：数据写入、查询和升级具备基本可靠性。

### 第四阶段：逐个增加其他领域

建议顺序：Schedule → Reminder → Transaction → Note → 跨领域关联。每个领域先完成创建、查询、修改、删除的基本闭环，再扩展筛选和边界条件。

### 第五阶段：Agent 接入

最后验证 JSON 输入输出、错误码、退出码和进程调用契约。

## 12. 第一轮真正应该写的测试

为了避免第一天就陷入几十个测试的实现工作，建议先只写下面 8 个：

- [ ] CLI-001：显示帮助信息
- [ ] DB-001：首次运行初始化 SQLite

- [ ] TASK-010：通过 ID 查询待办

这 8 个测试足以逼出 paadm 的基本链路：`CLI → Service → Repository → SQLite → JSON Response`。

暂时不要为了通过测试而提前实现所有功能。每次只写一个失败测试，再实现刚好足以让它通过的代码，随后重构。

## 13. 暂时不纳入第一版的测试

以下内容容易扩大项目范围，建议先不做：

- 自然语言日期解析（如“下周五下午”）。
- Agent 的意图识别准确率。
- 提醒的真实定时调度和消息推送。
- QQ、微信等消息平台适配。
- 多用户权限与账号系统。
- 分布式部署与多实例同步。
- 复杂的周期性日程规则。
- 复杂全文检索与语义搜索。
- 复杂统计和可视化。
- 自动推断、自动修改用户数据。

这些功能应在基础数据管理闭环稳定后，再单独设计测试。

## 14. 测试完成的判断标准

一个业务功能不能仅仅因为正常输入时能运行就算完成。至少需要：

1. 正常输入能够成功执行。
2. 缺少必要字段时能够拒绝。
3. 非法字段能够拒绝。
4. 查询不存在的数据时返回明确错误。
5. 修改和删除不会影响其他无关数据。
6. 进程重启后数据仍然存在。
7. JSON 输出符合约定。
8. 自动化测试可以重复运行，不依赖真实环境或人工操作。

**最终目标：让 paadm 成为一个可以独立使用、独立测试、结果可信的数据管理 CLI，而不只是 Agent 背后的数据库操作脚本。**
